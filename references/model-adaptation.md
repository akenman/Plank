```

"哪些模块划分方式会让依赖最少？"

Phase 2 前缀缓存利用：BLUEPRINT.md 修改时追加而非替换
追加接口签名的更新内容，缓存命中率可从 ~60% 提升到 ~90%

Phase 3 深度验证：运行时验证前用 thinking 预判
每条 @FLOW 最可能在哪步出错，优先测试高风险路径
```

## 新模型自动适配

不在表中的模型通过 4 个问题自分类：

```
1. 上下文窗口多大？
   ≥ 500K → 全量蓝图，释放阈值 65%
   200K → Phase 1 全量，Phase 2 按需
   128K → 仅当前模块+依赖

2. 是否支持 thinking？
   是 → 深度推理 + 预判高风险路径
   否 → 标准推理

3. 代码生成质量？
   高 → 抽样对照
   中 → 全量逐行
   需验证 → 全量 + 完整运行时验证

4. 是否支持子任务并行？
   是 → 同层 ≤ 3 并行
   否 → 串行
```

## 惰性探针

原设计中的"技能激活后立即运行 5 秒自测"存在问题：
1. 首次触发时 BLUEPRINT.md 可能还不存在
2. thinking token 的检测在大多数平台上不可控
3. 5 秒自测增加了不必要的延迟

改进为惰性探针——只在需要时检测：

```
探针 1 — 上下文加载验证（Phase 1 完成后触发）
  操作: 加载 BLUEPRINT.md，记录 token 消耗
  异常: 加载失败 → 降级为按需加载策略

探针 2 — 蓝图修改方式验证（首次修改 BLUEPRINT.md 时触发）
  操作: 正常修改蓝图
  异常: 追加失败 → 回退为替换模式

探针 3 — 并行能力验证（首次同层 ≥ 2 [empty] 时触发）
  操作: 尝试并行启动子任务
  异常: 创建失败 → 标记为串行

探针 4 — thinking 模式检测（Phase 1 推理时触发）
  操作: 观察首次推理输出
  异常: thinking 被截断 → 标记为无 thinking
```

探针结果记录在 CHECKPOINT.md：
```
@PROBE 2026-05-18 DeepSeek V4
  上下文: 全量加载 ✅
  缓存: 追加模式 ✅
  并行: 支持 ≤ 3 ✅
  thinking: 支持 ✅
```
